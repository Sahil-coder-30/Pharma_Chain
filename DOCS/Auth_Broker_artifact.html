§01 — THE GAP

The part nobody's users ever see

PharmaChain runs five separate frontends — manufacturer dashboard, shopkeeper dashboard, shopkeeper mobile, consumer mobile, and admin — and every one of them already has working login and registration, including Google sign-in for consumers. None of that is broken, and none of it needs to move.

What sits underneath is different. pharma-core is the service that actually signs and verifies every pack's cryptographic identity. It has no public ingress — it was only ever meant to be reachable by three other services: manufacturer-service, shopkeeper-service, and consumer-service. Right now, nothing formally proves to pharma-core which of those three is calling it, or whether the call is even allowed. That's a machine-identity problem, and it's a different problem from anything the five frontends solve.

§02 — ARCHITECTURE

One small broker, one public key set

The fix is a single new service whose only job is answering one question: is this service who it claims to be, and what is it allowed to do. It speaks OAuth2's client-credentials grant — each of the three services holds its own client ID and secret, and trades that for a short-lived, signed token. pharma-core stops trusting three separate baked-in secrets, and starts trusting one public key set, published in one place.

§03 — HOW ONE REQUEST ACTUALLY FLOWS

Six steps, all of them boring on purpose

  1. Each service is provisioned once. client_id + client_secret, stored as env vars

    manufacturer-service, shopkeeper-service, and consumer-service each get their own credential pair from the broker. Nothing is shared between them.

  2. A service asks the broker for a token. POST /oauth/token

    On startup, or whenever its cached token is close to expiring, the service sends its client ID and secret to the broker.

  3. The broker signs a short-lived token. ECDSA P-256, ~10–15 min TTL, role claim embedded

    The token carries who the caller is — manufacturer, shopkeeper, or consumer — not just that it's valid.

  4. The token lives in memory only. no disk, no Redis

    Each service instance holds its own copy. Reissuing one is cheap, so nothing needs to be shared across instances.

  5. The service calls pharma-core with it. Authorization: Bearer <token>

    Every call to pharma-core now carries proof of who's calling, not just network trust.

  6. pharma-core verifies and enforces. checks signature via cached JWKS, then checks role against the route

    If the role doesn't match what the route allows, the request is rejected before it reaches the ledger.

§04 — WHO'S ALLOWED TO DO WHAT

The role claim is the custody rule, enforced in code

A manufacturer ships. A shopkeeper sells. A consumer only ever looks. That's already true in the real world — the role claim is just what lets pharma-core refuse to let anyone break it.

Service Allowed / not allowed

§05 — IS THIS OVER-ENGINEERING?

What actually changes, and what stays exactly as it is

UNCHANGED

  • All five frontends' login and registration flows — Google sign-in included
  • pharma-core's existing pack-signing and JWKS logic for QR tokens
  • Every service's own business logic, routes, and database

NEW — AND DELIBERATELY NARROW

  • One stateless service, two endpoints: issue a token, publish public keys
  • No business data, no ledger access, no user records held by it
  • One trust root instead of three separate ad hoc assumptions
The honest cost: this is one more service to deploy and watch, and it does become the one place machine trust flows through. But it can't mint a pack, mark one sold, or write to the ledger — the worst a fault in it can do is fail closed, not misfire a custody transition. And for a hackathon build, an in-memory token per instance was chosen over a shared cache like Redis on purpose: a token is cheap enough to reissue that caching it across a network hop would spend real infrastructure cost to save a call that barely happens.

§06 — BUILD CHECKLIST

What the broker itself needs

  • POST /oauth/token — client_credentials grant; validates client_id/secret, returns an ECDSA P-256–signed JWT with a role claim, ~10–15 min expiry
  • GET /.well-known/jwks.json — public keys only, versioned by key ID so they can rotate without breaking a token mid-flight
  • A small client registry — client_id, hashed secret, role. Three rows is enough to start.
  • Verification middleware inside pharma-core — cache the JWKS, check the signature, check the role against a per-route permission table, reject before the ledger is touched
  • No shared token store — each instance holds its own token in memory, re-asks the broker on near-expiry or a 401

§07 — FOR THE ROOM

Every login our users make was already solved before this — that part doesn't change. What we built is the one piece that wasn't: a way for our own services to prove who they are to each other before anything touches the custody ledger.

A manufacturer's service physically cannot mark a pack sold. Only a shopkeeper's service can — because that's who's allowed to make a sale in the real world, and now it's true in the code too.
